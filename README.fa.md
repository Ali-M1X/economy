## ۱. کلید FRED (رایگان)

1. در <https://fredaccount.stlouisfed.org/login/secure/> حساب بسازید.
2. به <https://fredaccount.stlouisfed.org/apikeys> بروید و روی **Request API Key** بزنید. یک جمله درباره‌ی کاربرد کافی است (مثلاً «research dashboard»).
3. کلید ۳۲ کاراکتری را کپی کنید. در مرحله‌ی ۴ آن را با نام `FRED_API_KEY` ذخیره می‌کنید.

این کلید سه چیز را باز می‌کند: نسخه‌های تاریخی داده (ALFRED)، که برای بک‌تست بدون «نگاه به آینده» لازم است؛ تاریخ انتشار گزارش‌ها؛ و زمان به‌روزرسانی هر سری.

(اختیاری) `BLS_API_KEY` از <https://data.bls.gov/registrationEngine/> سقف درخواست‌های BLS را بالا می‌برد.

## ۲. ربات تلگرام

1. در تلگرام با **@BotFather** گفتگو کنید، دستور `/newbot` را بفرستید، نام و نام کاربری ربات را بدهید.
2. توکنی به شکل `123456789:AA...` می‌گیرید. این توکن همان `TELEGRAM_BOT_TOKEN` است.
3. مقصد پیام‌ها را انتخاب کنید:
   - **کانال:** ربات را به کانال اضافه کنید و **ادمین** کنید (اجازه‌ی ارسال پیام). شناسه‌ی کانال عمومی `@channelname` است. برای کانال خصوصی، شناسه عددی و به شکل `-100...` است.
   - **گروه یا گفتگوی شخصی:** یک پیام به ربات (یا در گروه) بفرستید. سپس در مرورگر نشانی `https://api.telegram.org/bot<TOKEN>/getUpdates` را باز کنید و عدد `chat.id` را بردارید.
4. این شناسه همان `TELEGRAM_CHAT_ID` است.

> توکن ربات مثل رمز عبور است. اگر لو رفت، در BotFather با `/revoke` آن را باطل کنید.

## ۳. کلید Claude (Anthropic)

1. در <https://console.anthropic.com> حساب بسازید، روش پرداخت ثبت کنید و در بخش **API Keys** یک کلید بسازید. این کلید همان `ANTHROPIC_API_KEY` است.
2. مدل پیش‌فرض `claude-sonnet-5` است. برای تغییر، متغیر `CLAUDE_MODEL` را تنظیم کنید؛ مثلاً `claude-sonnet-5-5` که نسخه‌ی جدیدتر Sonnet با همان قیمت است.
3. هزینه: اخبار هر ۱۵ دقیقه فقط برای آیتم‌های **جدید** طبقه‌بندی می‌شوند. هر آیتم یک بار فرستاده می‌شود. متن توضیحی فقط در گزارش‌ها نوشته می‌شود. برای کنترل هزینه در کنسول Anthropic سقف ماهانه (spend limit) بگذارید.

**Claude هیچ عددی تولید نمی‌کند.** دو کار انجام می‌دهد:
- اخبار و اسناد فدرال را طبقه‌بندی می‌کند؛
- پاراگراف «زنجیره علّی» را فقط از اعداد محاسبه‌شده می‌نویسد.

اگر در متن Claude عددی باشد که در داده‌های محاسبه‌شده نیست، آن متن کنار گذاشته می‌شود و متن قالبی جایگزین آن می‌شود.

## ۴. GitHub Secrets و Variables

در مخزن به **Settings → Secrets and variables → Actions** بروید.

**Secrets** (در زبانه‌ی *Secrets* با **New repository secret**):

| نام | مقدار |
|---|---|
| `FRED_API_KEY` | کلید مرحله‌ی ۱ |
| `TELEGRAM_BOT_TOKEN` | توکن مرحله‌ی ۲ |
| `TELEGRAM_CHAT_ID` | شناسه‌ی مرحله‌ی ۲ |
| `ANTHROPIC_API_KEY` | کلید مرحله‌ی ۳ |
| `BLS_API_KEY` | اختیاری |
| `DATABASE_URL` | اختیاری، مرحله‌ی ۷ |

**Variables** (در زبانه‌ی *Variables*):

| نام | مقدار | کاربرد |
|---|---|---|
| `DASHBOARD_URL` | نشانی داشبورد (مرحله‌ی ۶) | لینک در انتهای پیام‌ها |
| `PUBLISH_SNAPSHOT` | `true` | انتشار آخرین داده برای داشبورد آنلاین |
| `CLAUDE_MODEL` | اختیاری | تغییر مدل Claude |
| `ENABLE_DB_STORAGE` | `true` فقط پس از مرحله‌ی ۷ | ذخیره در پایگاه داده |

بدون کلیدهای تلگرام، پیام‌ها ارسال نمی‌شوند. به‌جای آن در پوشه‌ی `output/outbox/` ذخیره می‌شوند و در artifact اجرای workflow قابل دانلودند؛ برای آزمایش پیش از ساخت ربات مفید است.

## ۵. فعال‌سازی زمان‌بندی

GitHub کارهای زمان‌بندی‌شده (`schedule`) را **فقط از شاخه‌ی پیش‌فرض** (`main`) اجرا می‌کند.
1. شاخه‌ی توسعه را در `main` ادغام کنید (Pull Request → Merge).
2. در زبانه‌ی **Actions** روی workflow به نام **schedule** بروید و **Run workflow** را بزنید. mode را `report` بگذارید تا یک گزارش کامل ساخته و ارسال شود.
3. خروجی را بررسی کنید: پیام تلگرام، خلاصه‌ی job و artifact به نام `data-availability`.

## ۶. داشبورد روی Streamlit Community Cloud

1. متغیر `PUBLISH_SNAPSHOT=true` را بسازید (مرحله‌ی ۴). یک بار workflow **data-availability** را اجرا کنید تا فایل `snapshot-latest` در بخش **Releases** مخزن ساخته شود.
2. در <https://share.streamlit.io> با GitHub وارد شوید و **Create app** بزنید. مخزن و شاخه‌ی `main` را انتخاب کنید و Main file path را `dashboard/app.py` بگذارید.
3. در **Advanced settings → Secrets** بنویسید:
   ```toml
   MACRO_PULSE_SNAPSHOT_URL = "https://github.com/<owner>/<repo>/releases/download/snapshot-latest/snapshot.tar.gz"
   ```
4. **Deploy** را بزنید. نشانی به‌دست‌آمده را در متغیر `DASHBOARD_URL` بگذارید.

داشبورد به هیچ کلیدی نیاز ندارد. داده‌ها هر بار که pipeline اجرا شود تازه می‌شوند؛ دست‌کم روزی یک بار، و پس از هر انتشار مهم. قیمت BTC و طلا (PAXG) هر ۶۰ ثانیه از صرافی‌ها به‌روز می‌شود. این فایل فقط داده‌ی عمومی بازار است و چون مخزن عمومی است، فایل release هم عمومی است.

## ۷. پایگاه داده Supabase (اختیاری)

سامانه بدون پایگاه داده هم کار می‌کند؛ از snapshot استفاده می‌کند. پایگاه داده برای **تاریخچه‌ی گزارش‌ها و سیگنال‌ها** و نگه‌داری داده‌های لحظه‌ای (دفتر سفارش، قراردادهای باز) است.

1. در <https://supabase.com> یک پروژه‌ی جدید بسازید (Region نزدیک به آمریکا، مثلاً `us-east-1`) و یک **رمز عبور قوی** برای پایگاه داده بگذارید.
2. در **Project Settings → Database → Connection string → URI** گزینه‌ی **Session pooler** را انتخاب کنید. نشانی به این شکل است:
   `postgresql://postgres.<ref>:<PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres`
   - نشانی مستقیم `db.<ref>.supabase.co` فقط IPv6 است و از GitHub Actions در دسترس نیست.
   - اگر رمز شامل `@`، `:`، `/` یا `#` است، آن را **URL-encode** کنید (مثلاً `@` ← `%40`) یا رمزی بدون این نویسه‌ها انتخاب کنید.
3. این نشانی را در Secret به نام `DATABASE_URL` بگذارید و متغیر `ENABLE_DB_STORAGE=true` را بسازید.
4. جدول‌ها و سیاست‌های امنیتی (RLS) در اولین اجرا خودکار ساخته می‌شوند (`python -m db.migrate`). فایل‌های `db/migrations/*.sql` را می‌توانید در **SQL Editor** سوپابیس هم اجرا کنید.
5. workflow **data-availability** را اجرا کنید. در خلاصه‌ی job باید تعداد ردیف‌های ذخیره‌شده دیده شود.

## زمان‌بندی و محدودیت‌های GitHub Actions

| زمان (UTC) | زمان تهران | کار |
|---|---|---|
| هر ۱۵ دقیقه | — | بررسی اخبار، طبقه‌بندی با Claude، هشدار برای خبرهای مهم (★۴ و بالاتر). خبر ★۵ یک گزارش کامل هم می‌سازد |
| هر روز ۱۴:۴۰ | ۱۸:۱۰ | به‌روزرسانی کامل داده، **هشدار یک روز قبل** برای انتشارهای فردا، بررسی سلامت داده |
| ۵ دقیقه پس از هر زمان انتشار (برای هر دو ساعت تابستانی و زمستانی آمریکا) | — | اگر گزارشی منتشر شده باشد: انتظار تا ظاهر شدن عدد جدید (حداکثر ۲ ساعت)، سپس داده، ضرایب، امتیازها، تکنیکال، سیگنال‌ها و در پایان تلگرام |
| شنبه ۰۳:۲۰ | ۰۶:۵۰ | محاسبه‌ی دوباره‌ی ضرایب و بک‌تست‌ها و **خلاصه‌ی هفتگی** |
| هر ساعت (دقیقه ۵۰) | — | فقط وقتی CPI، PCE، NFP یا FOMC در ۷۲ ساعت آینده است: بررسی زنده‌ی پیش‌موقعیت‌گیری؛ هشدار فقط برای ترکیب‌های دارای برتری اثبات‌شده |

محدودیت‌ها:
- ساعت‌های cron فقط UTC هستند؛
- اجراها ممکن است چند دقیقه دیر شروع شوند یا در شلوغی حذف شوند؛
- کمترین فاصله ۵ دقیقه است؛
- اگر در مخزن عمومی **۶۰ روز** فعالیتی (commit) نباشد، GitHub زمان‌بندی را غیرفعال می‌کند. برای فعال‌سازی دوباره به زبانه‌ی Actions بروید؛
- برای مخزن عمومی، دقیقه‌های اجرا رایگان است.

اگر داده‌ی اصلی خطا داشته باشد یا کهنه باشد، به‌جای گزارش یک **هشدار سلامت داده** ارسال می‌شود. هشدار تکراری تا ۱۲ ساعت دوباره فرستاده نمی‌شود.

## سیگنال‌های پیش‌موقعیت‌گیری (پیش از انتشار)

این بخش بررسی می‌کند که آیا بازار **پیش از** انتشار CPI، PCE، NFP یا تصمیم FOMC در یک جهت موقعیت گرفته است. سپس می‌سنجد که آیا این موقعیت‌گیری در گذشته حرکت پس از انتشار را پیش‌بینی کرده یا نه.

نشانه‌ها:
- رانش قیمت نسبت به نوسان عادی همان ساعت‌های هفته؛
- یک‌طرفه و کم‌نوسان بودن حرکت؛
- عدم‌توازن سفارش‌های تهاجمی؛
- تغییر بازده ۲ ساله؛
- تغییر قراردادهای باز و نرخ تأمین مالی بیت‌کوین؛
- داده‌های پیشرو (ADP پیش از NFP، و CPI و PPI پیش از PCE).

هر نشانه فقط از داده‌ای استفاده می‌کند که در همان لحظه موجود بوده است.

برای هر انتشار، پنجره‌های ۶، ۱۲، ۲۴، ۴۸ و ۷۲ ساعته جداگانه و **خارج از نمونه** آزمون می‌شوند. پنجره‌ی هر رویداد هم فقط از روی رویدادهای گذشته انتخاب می‌شود. سیگنال زنده فقط وقتی به تلگرام می‌رود که همان ترکیب انتشار و دارایی سه شرط را داشته باشد: دست‌کم ۳۰ معامله‌ی خارج از نمونه، میانگین R مثبت، و p کمتر از ۰٫۰۵. در غیر این صورت ستاپ فقط در زبانه‌ی «پیش‌موقعیت‌گیری» داشبورد نمایش داده می‌شود. اگر برای انتشاری هیچ برتری‌ای پیدا نشود، همین صریحاً گزارش می‌شود.

جریان آتی وجوه فدرال و عدم‌توازن دفتر سفارش تاریخچه‌ی رایگان ندارند. این دو فقط به‌صورت زنده نمایش داده می‌شوند و در امتیاز بک‌تست‌شده نیستند (جزئیات در DATA_GAPS.md).

## انتقال به VPS (چک‌لیست)

همان زمان‌بندی با `docker compose` روی سرور اجرا می‌شود (`jobs/runner.py` با همان cronها). داشبورد هم در همان سرور است.

- [ ] سرور لینوکس (Ubuntu 22.04+ با ۲ گیگ RAM کافی است). ترجیحاً **خارج از آمریکا**، تا Bybit و Binance Futures هم در دسترس باشند (از IPهای آمریکا مسدودند).
- [ ] نصب Docker: `curl -fsSL https://get.docker.com | sh`
- [ ] `git clone` مخزن، سپس `cp .env.example .env` و پر کردن کلیدها. سطح دسترسی فایل را محدود کنید: `chmod 600 .env`
- [ ] `docker compose up -d --build`
- [ ] بررسی: `docker compose logs -f scheduler` (اولین اجرا یک به‌روزرسانی کامل است، حدود ۵ دقیقه) و `docker compose ps` (وضعیت healthy)
- [ ] داشبورد فقط روی `127.0.0.1:8501` باز است. برای دسترسی از بیرون یک reverse proxy با HTTPS بگذارید؛ مثلاً Caddy با یک خط `your.domain { reverse_proxy 127.0.0.1:8501 }`. برای ورود هم احراز هویت پایه (basic auth) اضافه کنید.
- [ ] فایروال: فقط پورت‌های 22، 80 و 443 باز باشند (`ufw allow OpenSSH && ufw allow 80,443/tcp && ufw enable`)
- [ ] ساعت سرور روی UTC و همگام (NTP) باشد: `timedatectl`
- [ ] پشتیبان: volume به نام `macro-pulse-data` (پوشه‌های runs، state و current). اگر Supabase فعال است، تاریخچه آنجاست.
- [ ] به‌روزرسانی کد: `git pull && docker compose up -d --build`
- [ ] پس از اطمینان از کار سرور، workflow به نام **schedule** را در GitHub غیرفعال کنید (Actions → schedule → Disable) تا پیام‌ها دو بار ارسال نشوند.
- [ ] `DASHBOARD_URL` را روی نشانی جدید تنظیم کنید.

اجرای دستی روی سرور:
```bash
docker compose run --rm scheduler python -m jobs.pipeline --mode report --runs-dir /data/runs --state /data/state
docker compose run --rm scheduler python -m jobs.notify health --root /data/current
```

## اجرای محلی (برای توسعه)

```bash
pip install -r requirements-dev.txt
python -m pytest -q                          # همه‌ی آزمون‌ها، بدون اینترنت

python -m jobs.notify report --root /tmp/demo --dry-run   # پیش‌نمایش پیام‌ها در output/outbox
```

## داده‌هایی که رایگان در دسترس نیستند

جزئیات و وضعیت هر مورد در [DATA_GAPS.md](DATA_GAPS.md) است. خلاصه:

| مورد | جایگزین رایگان فعلی | بهترین گزینه‌ی پولی |
|---|---|---|
| پیش‌بینی اجماع تحلیلگران (برای «شگفتی» واقعی) | «انتظار» = میانگین ۳ دوره‌ی قبل | Trading Economics API یا Bloomberg ECO |
| شاخص ISM (PMI) | نظرسنجی‌های فیلادلفیا و نیویورک | اشتراک ISM یا S&P Global PMI |
| نقشه‌ی لیکوئیدیشن و داده‌ی Coinglass | عمق دفتر سفارش، قراردادهای باز، تخمین خوشه‌های لیکوئیدیشن | Coinglass API یا Kaiko |
